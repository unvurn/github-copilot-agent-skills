# C# ユニットテストの作成

## 初回起動時の文書確認

テスト生成に着手する前に、次の手順を必ず実行します。設定ファイルは、このスキルと同じディレクトリにある `SETTINGS.md` です。`SETTINGS.md` は利用者（Copilot に依頼している人）が手動で編集できる設定として扱います。

1. `SETTINGS.md` を読み込みます。`status: approved` かつ `use: yes` の項目は、起動回数にかかわらず、記録された `path` の最新内容を毎回読み込みます。
2. 設定が未登録、`status: pending`、または `status: not-found` の項目について、コードベース内を検索し、次の記述を持つファイルの所在を調べます。
   - コーディング規約書
   - ユニットテストガイドライン
3. 検索結果として、各項目について候補ファイルのパス、内容の概要、検索にかかった時間を利用者に提示し、今後その文書を使用してよいか確認します。候補が複数ある場合はすべて提示します。
4. 利用者が肯定した文書は、`SETTINGS.md` に `status: approved`、`use: yes`、採用した `path` として記録し、以後のユニットテスト生成に使用します。
5. 利用者が否定した場合は、コードベース外を含む別の所在を利用者に尋ねます。指定されたローカルパスまたは URL があれば、その文書を読み込んでテストコード生成に使用し、`SETTINGS.md` に記録します。指定がなければ、既存コードベースのスタイルを参考にして生成します。
6. 検索に1分以上かかった場合は、実測時間を `SETTINGS.md` に記録し、該当項目の `search-disabled: yes` とします。以後、その項目について自動的な再検索は行わず、文書の所在を利用者に確認します。
7. `SETTINGS.md` に保存できなかった場合だけ、初回起動時と同じ所在検索を行います。再検索した場合も必ず実測時間を記録し、1分以上なら以後の再検索を無効化します。

文書の内容が古い可能性がある場合でも、設定された文書は毎回読み込み、常にその時点の最新内容に基づいて処理します。設定の `path`、`status`、`use`、検索記録は利用者が直接変更できます。

## 回答の言語に関する規則

確認への回答は、利用者が使用する言語に関係なく意味に基づいて解釈します。`yes` または `no` という文字列との一致を必須にしません。

- 肯定を意味する回答（例: `yes`、`はい`、`承認`、`使用してよい`）は `yes` として扱います。
- 否定を意味する回答（例: `no`、`いいえ`、`拒否`、`使用しない`）は `no` として扱います。
- 他の言語の同等表現、自然な文章、明確な肯定・否定も同じ規則で意味を解釈します。
- 回答が曖昧、条件付き、または肯定・否定の判定ができない場合は、どちらの意味かを利用者に確認します。推測で設定を変更しません。
- 設定ファイルへ記録するときは、言語に関係なく正規化された `yes` または `no` を使用します。

## ワークフロー

1. テスト対象の本番コードの型またはメソッドを特定し、公開契約、依存する協力オブジェクト、境界値、既存テストを確認します。
2. 関連するテストプロジェクトを特定し、プロジェクトファイルを読んで、ターゲットフレームワーク、テストフレームワーク、アサーションの書式、利用可能なヘルパーを確認します。
3. リポジトリの既存規約を再利用します。利用可能なテスト環境が存在しない場合を除き、別のテストフレームワークやパッケージを追加しません。
4. 観測可能な振る舞いを検証するために、必要最小限のテストを追加します。
   - 代表的な正常系
   - 関係する場合は、境界値または空の入力
   - 契約で定められている場合は、不正な入力または失敗時の振る舞い
   - 振る舞いの一部である場合に限った、協力オブジェクトとのやり取り
5. テストを分離し、決定的にします。テストに明確な理由がない限り、実際のネットワーク呼び出し、時刻、乱数、ファイルシステムの状態、スリープ、共有された可変状態を使用しません。
6. テスト名はローカルの規約に従います。`Method_WhenInputIsInvalid_ThrowsArgumentException` のように、シナリオと期待結果が分かる名前を優先します。
7. テストフレームワークが提供するライフサイクル、パラメーター化、アサーション、非同期処理を使用します。準備、実行、検証の各手順を読み取りやすく保ちます。
8. まず最も関連性の高い狭い範囲のテストを実行し、その後、可能であればテストプロジェクトまたはソリューション全体を実行します。
9. 変更したファイル、実行した検証コマンド、その結果を報告します。未検証の振る舞いや環境上の障害があれば、明確に記載します。

## フレームワークに関する注意

- NUnit では、`[Test]`、`[TestCase]`、`[TestCaseSource]` を使用します。`[SetUp]` は各テストで共有する初期化に限って使用し、ローカルの書式に合う場合は `Assert.That` を使用します。
- xUnit では、`[Fact]`、`[Theory]`、コンストラクターによる初期化を使用します。共有状態が意図されたものでない限り、xUnit のコレクションフィクスチャは使用しません。
- MSTest では、既存プロジェクトの規約に従って `[TestClass]`、`[TestMethod]`、`[DataTestMethod]`、`[DataRow]` を使用します。
- 非同期メソッドをテストする場合、テストメソッドの戻り値を `Task` にして処理を await します。`.Result` や `.Wait()` でブロックしません。

## 検証

リポジトリのターゲットフレームワークとテストプロジェクトのパスを使用します。代表的なコマンドは次のとおりです。

```powershell
dotnet test path\to\TestProject.csproj --filter FullyQualifiedName~ClassName
```

対象を絞ったテストが成功したら、次のコマンドを実行します。

```powershell
dotnet test path\to\TestProject.csproj
```

リポジトリでソリューション単位のテストコマンドを使用している場合は、最終検証にそのコマンドを優先します。

## 品質基準

- テストは、対象の不具合が存在する場合に失敗し、意図した振る舞いでは成功する必要があります。
- private な実装詳細ではなく、外部から観測できる結果をアサートします。
- 各テストは1つの振る舞いに集中させます。
- テストを通すことだけを目的に、本番コードやアサーションを弱めません。
- 関係のないテスト、フォーマット、プロジェクトメタデータは変更しません。
